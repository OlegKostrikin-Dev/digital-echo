# ADR-004: Псевдонимизация сторон через HMAC с ключом на стороне ИВЦ

**Дата:** 2026-07-15
**Статус:** Принято (на нашей стороне; требует явной фиксации в форматах обмена с ИВЦ)

## Контекст

Черновик обмена данными ([data-exchange/proposal-anonymized-data.md](../data-exchange/proposal-anonymized-data.md),
раздел 5) предлагает заменять БИН сторон сделки хэшем и в качестве примера
называет «стойкий алгоритм, например SHA-256». ИВЦ подтвердил стабильное
одностороннее хэширование (ответ на вопрос 3).

Проблема: пространство БИН крошечное и публичное. БИН — 12 цифр, реестры
налогоплательщиков открыты, действующих БИН — единицы миллионов. Простой
SHA-256 от БИН восстанавливается полным перебором по открытому реестру за
минуты на обычном ноутбуке. Такая «анонимизация» не защищает ничего:
любой обладатель выгрузки деанонимизирует весь граф.

Юридическая позиция всей схемы — «оператор расчёта не получает налоговую
тайну и конфиденциальные первичные данные» — держится ровно на
невозможности обратного восстановления идентификаторов. Если
восстановление тривиально, позиция не работает.

## Рассмотренные варианты

- **A. SHA-256(БИН)** — отвергнут: перебор по открытому реестру БИН.
- **B. SHA-256(соль + БИН) с общей солью, известной обеим сторонам** —
  отвергнут: раз соль известна нам, мы (и любой, к кому соль утечёт)
  можем выполнить тот же перебор.
- **C. HMAC-SHA-256(ключ, БИН), секретный ключ существует только в ИВЦ** —
  принят. Без ключа перебор невозможен; преобразование детерминировано,
  поэтому стабильность идентификатора между выгрузками сохраняется.
- **D. Случайный персистентный маппинг (таблица БИН → UUID на стороне ИВЦ)** —
  криптографически эквивалентен C, но требует ведения таблицы
  соответствий. Допустимая альтернатива, если ИВЦ так удобнее
  операционно; свойства для нас те же.

## Решение

Требуем в форматах обмена ключевое преобразование идентификаторов:
HMAC-SHA-256 с секретным ключом, который генерируется, хранится и
применяется только внутри ИВЦ (вариант C; вариант D — допустимая замена
по выбору ИВЦ). Формулировку «например, SHA-256» из следующей итерации
черновика убрать.

Требования к ключу:

- ключ никогда не передаётся нам и не включается ни в какие выгрузки;
- ротация ключа без пересчёта — запрещена: смена ключа делает новые
  выгрузки несопоставимыми со всей накопленной историей. Ротация
  возможна только с одновременным пересчётом (перевыгрузкой) всей
  истории новым ключом.

## Последствия

- Мы физически не можем сопоставить обезличенный идентификатор с БИН —
  это основа юридической позиции и аргумент для юристов ИВЦ.
- Обратное отображение «БИН → хэш» доступно только ИВЦ, поэтому выдача
  результата конкретной компании требует участия ИВЦ — см.
  [ADR-005](005-ecp-resolve-flow.md).
- Компрометация ключа ИВЦ обесценивает псевдонимизацию всей истории —
  режим хранения ключа (HSM или эквивалент) стоит проговорить при
  согласовании форматов.
